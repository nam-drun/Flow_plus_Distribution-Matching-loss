# Why care?
Current SOTA in image generation is MDP + RLHF. For example, see [Qwen Image 2.0 technical reports](https://arxiv.org/pdf/2606.27608v1)). Recently, people have figured out that you can post-train flow models with various distribution matching losses such as:
- Fréchet distance, see [FD loss paper](https://arxiv.org/abs/2604.28190).
- Adversarial GAN on Fréchet distance, see [AdvFD loss paper](https://arxiv.org/abs/2608.11205).
- KL, see [TDM paper](https://arxiv.org/abs/2503.06674) and [Mgflow paper](https://arxiv.org/abs/2609.35763).

We argue that all these papers including the current SOTA share the same common in utilising post-training to counteract the discretisation error produced by pretrained model (be it Flow or MDP). The last part is interesting because MDP's connection to Flow Matching isn't clear. From [Flow-GRPO paper](https://arxiv.org/abs/2505.05470), we learn that in order to use RLHF (since you can't just make RLHF working with Flow Matching directly), you first need to formulate the flow process (or multi-step denoising process) as Markov Decision Process (MDP). This comes at the cost of making the "decision" or "transition" part very degenerate. E.g., The state transition is literally just modelling the sampling of the action $a \sim p(a|x)$ as a dirac delta on the chosen $a$ (i.e. you get the sampling action without leaving "density" language: you use the fact that $\mathbb{E}_{X \sim p(x)}[\delta_X] = p(x)$, i.e. in some sense this passes through the density like an identity). If you want to formally connect MDP to Flow Matching, you need to go via Hamilton-Bellman-Jacobi <-> Hamilton-Jacobi <-> Wasserstein, where Flow Matching is built from Wasserstein space (see section 3.4 in [Stochastic Interpolant paper](https://arxiv.org/abs/2303.08797)). In short, there's some chance that MDP is connected to Flow Matching, but it's not clear. What is clear is that MDP is nowhere near as compute efficient as Flow Matching. 

Because it's not a clear yes or no on whether MDP is actually connected to Flow Matching; and because Flow + post train with distribution matching loss actually works, where KL works best compared to FD and AdvFD by a large margin; and because KL is an important term in GRPO loss, see equation (3) in [Flow-GRPO paper](https://arxiv.org/abs/2505.05470). Altogether, these open up 2 interesting scenarios. 
1. Maybe MDP turns out to be the "distant prodigy heir" of Flow Matching, where it takes KL term to "unlock" the potential of MDP during post-training with RLHF. This means that everyone should migrate to MDP + RLHF for image generation.
2. Or maybe MDP is not the distant prodigy heir. So practitioners have 2 choices: if having lots of compute to post-train, use MDP + RLHF; if not, use Flow + KL. This is because Flow Matching is already much more compute efficient than MDP, and post-training with distribution matching loss only makes Flow Matching even more compute efficient.
   
In this work, we investigate to see which scenario is more likely true.

# How can discretisation error be counteracted?
First, let's speedrun understanding in modern diffusion/flow matching. If you sample any distribution, you will get a point cloud. The idea behind Optimal Transport is that if you literally move (i.e., transport) all samples ("points") from their starting points $X_0$ to some end points $X_1$, then you will get a different distribution $P_1$ (unless somehow $X_0 = X_1$). Now suppose $P_1$ is identical to data distribution $P^*$ and $P_0 = \mathcal{N}(0, I_d)$, then you have discovered flow matching. The next step to figure out how to train the neural network. In high school physics, you have learnt about *displacement = velocity x time*. Same idea applies for "transport". During sampling, given $X_0 \sim \mathcal{N}(0, I_d)$, you "transport" that sample to $X_1$ using *next position = current position + velocity x time* (this is literally the case if you use Euler integration solver, but still holds somewhat true for more accurate solvers like Heun and Dormand-Prince 5(4)). During training, you train neural network to learn ground truth velocity field $v(t, x)$ via mean-squared error (there's a reason why it's called "velocity field" rather than just "velocity"). So where is $v(t, x)$ coming from? In high school physics, we learn that velocity = derivative of current position $X_t$. Same idea applies here. First, you sample a random pair of `start point, end point`: $`\left\{X_0, X_1\right\}`$ with start point $X_0$ being pure noise and end point $X_1$ being accessible image during training. Then you compute $X_t$ using noise schedule $\alpha_t$ and $\beta_t$. E.g., if you use VP schedule from DDPM diffusion, then $X_t = \sqrt{1 - t^2}X_0 + tX_1$; if you use linear schedule from [JiT paper](https://arxiv.org/abs/2511.13720v1) then $X_t = (1-t)X_0 + tX_1$. From $X_t$, you take its derivative $\dot{X}_t$ to acquire velocity $v(t, X_t)$. Now, if multiple trajectories intersect at some random point $X_t = x$, you can't really feed multiple "velocities" to the neural network. So the compromise is to take their averages $v(t, x) = \mathbb{E}[\dot{X}_t \mid X_t = x]$, hence why we use the term "velocity field" $v(t, x)$ instead of "velocity" $v(t, X_t)$ (or $\dot{X}_t$) in modern diffusion/flow matching. But, if the ambient space $\mathbb{R}^d$ has high number of dimensions (which is always true in image generation), then $\mathbb{E}[\dot{X}_t \mid X_t = x] \approx \dot{X}_t$. So it's fine to treat "velocity field" as if it is "velocity". For diffusion, you add-on random noise during sampling, whether this is practically useful or not is questionable.

Second, we want to establish an idea that for the same solver and the same amount of sampling steps, direction of discretisation error is consistent in term of direction and displacement - see the picture below. In the picture below, look at direction and displacement between Base Continuous vs Base Euler; and look at direction and displacement between Perturbed Continuous vs Perturbed Euler, you will see that their direction and displacement are the same. This is not a coincidence and we'll analyse this using Alekseev-Grobner formula in a separated post.
